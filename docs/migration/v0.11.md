# Migration Guide: v0.10 → v0.11

This guide covers the breaking changes and behaviour changes in v0.11.

- [**Asynchronous `payment.topUp`**](#asynchronous-paymenttopup), the call now registers a top up and returns; the
  outcome arrives on a status subscription
- [**Strict fixed-size `Bytes` and `Hex`**](#strict-fixed-size-bytes-and-hex), a wrong-length value is an error, not
  zero-padded
- [**Subscription interrupts**](#subscription-interrupts), every subscriber sees them, late listeners included

> **v0.11 is wire-incompatible with v0.10 for `host_payment_top_up`**, whose request and error shapes changed, so hosts
> and products must be upgraded together. Every other method is byte-identical. There is no session or key impact.

---

## Asynchronous `payment.topUp`

`host_payment_top_up` used to hold its response open until the host had finished claiming, and reported a short claim as
a `PartialPayment { credited }` error. It now returns as soon as the top up is **registered**, and the outcome is
streamed from a new `host_payment_top_up_status_subscribe`.

Both sides change shape, so hosts and products must be upgraded together. The rest of the protocol is untouched: the new
subscription is appended after every existing method, so no method id moves.

### The id is supplied by the product

`topUp` takes an id chosen by the caller instead of returning one. A product can be terminated between the call and its
response, which would lose a host-issued id and with it any way to ask what happened; an id the product wrote down first
survives that.

The id is an opaque **32-byte** value — `[u8; 32]` on the wire, `Uint8Array` in TypeScript, the same shape as a raw
RFC-0022 derivation index. It is also the idempotency key: registering an id the host already knows fails with
`AlreadyExists` rather than starting a second top up, so a retry after an ambiguous failure is safe.

### The host owns the operation once it is registered

A registered top up is driven to a terminal status by the host, across a full host restart if need be. Statuses never
advance once terminal, no action is taken after that point, and they are kept indefinitely — a product that comes back
much later can still subscribe and learn the outcome.

### One live top up per source

A source can back only one top up at a time. Registering a second one against a source whose previous top up has not
reached a terminal status (`Claimed { finalized: true }`, `ClaimedPartially` or `NotClaimed`) fails with `SourceBusy`;
the source is reusable once that status arrives. Because the host cannot tell two concurrent claims on the same source
apart, this is a rejection rather than a queue — wait for the terminal status, then register again with a fresh id.

### Products

```ts
// v0.10
await payments.topUp(1_000_000n, { type: 'productAccount', derivationIndex: 0 });
// resolved only once the funds had been claimed; threw PartialPaymentErr on a short claim

// v0.11
const id = crypto.getRandomValues(new Uint8Array(32)); // persist this before calling
await payments.topUp(1_000_000n, { type: 'productAccount', derivationIndex: 0 }, id);
// resolves as soon as the host registered the top up

const sub = payments.subscribeTopUpStatus(id, status => {
  switch (status.type) {
    case 'detecting': // waiting for the amount to appear on the source
    case 'claiming':
      return;
    case 'claimed':
      if (status.finalized) done(); // terminal
      return;
    case 'claimedPartially':
      return short(status.actualClaimed); // terminal
    case 'notClaimed':
      return failed(); // terminal
  }
});
sub.onInterrupt(reason => {
  // PaymentTopUpStatusErr.NotFound — the host does not know this id
});
```

The optional trailing purse argument (`into`) is unchanged and now sits after the id:
`topUp(amount, source, id, into?)`.

### Hosts

`handlePaymentTopUp` gains `id` on its params and MUST return without waiting:

```ts
container.handlePaymentTopUp(async ({ amount, source, id }, { ok, err }) => {
  // `id` arrives as a raw 32-byte Uint8Array — key storage by its hex form.
  const key = toHex(id);
  if (topUps.has(key)) return err(new PaymentTopUpErr.AlreadyExists());
  if (topUps.hasLiveFor(source)) return err(new PaymentTopUpErr.SourceBusy());
  topUps.register(key, { amount, source });
  return ok(undefined);
});
```

and the outcome moves to the new handler:

```ts
container.handlePaymentTopUpStatusSubscribe((id, send, interrupt) => {
  const topUp = topUps.get(toHex(id));
  if (!topUp) {
    interrupt(new PaymentTopUpStatusErr.NotFound());
    return () => {};
  }
  return topUp.track(send);
});
```

A host that registers no `handlePaymentTopUpStatusSubscribe` interrupts every such subscription with
`PaymentTopUpStatusErr.Unknown`, as with the other unimplemented subscriptions.

### `PaymentTopUpErr` lost two variants and gained two

```ts
// v0.10
PaymentTopUpErr.InsufficientFunds;
PaymentTopUpErr.PartialPayment; // carried { credited }
PaymentTopUpErr.InvalidSource;
PaymentTopUpErr.Unknown;

// v0.11
PaymentTopUpErr.InvalidSource;
PaymentTopUpErr.AlreadyExists; // this id is already registered
PaymentTopUpErr.SourceBusy; // this source still has a non-terminal top up
PaymentTopUpErr.Unknown;
```

Neither removed variant has an answer at registration time any more. A source that is short of the amount is not a
failure — the host sits in `Detecting` waiting for the funds — and a short claim is the
`ClaimedPartially { actualClaimed }` status. Code that matched on `InsufficientFunds` or read
`PartialPaymentErr.credited` moves to the status subscription.

`ClaimedPartially` in practice means the source never accumulated enough balance to cover `amount` — pre-funding
transfers that got re-orged away, typically; the recovery is to send the remainder to the source. It also covers an
`amount` below the smallest coinage denomination, where the host claims `amount - amount % 2^min_coinage_exponent`.
`NotClaimed` most likely means the host never observed any balance at the source at all.

## Strict fixed-size `Bytes` and `Hex`

`Bytes(n)` and `Hex(n)` from `@novasamatech/scale` back every fixed-size protocol field: account ids, genesis hashes and
chain ids, public and private keys, VRF outputs, and the new 32-byte top up id. Encoding used to accept a shorter value
and zero-pad it to `n`, so `0x22` and `0x22` followed by 31 zero bytes were the same thing on the wire and any two ids
that differed only in a missing tail collided on the host. Encoding now throws unless the value is exactly `n` bytes:

```
Bytes(32): expected 32 bytes, got 16
```

Decoding was already strict. `Hex(n)` counts bytes, not hex characters: `Hex(32)` wants 64 hex digits after `0x`.

Where the error surfaces depends on the call:

- a **request** rejects with the method's `Unknown` error, the codec message in `payload.reason`, because encoding
  happens inside the transport's async request path;
- a **subscription** throws synchronously from the `subscribe*` call, before anything reaches the host, because the
  start payload is encoded to build the multiplexing key.

```ts
// v0.10: silently sent 0x22 followed by 31 zero bytes as the chain id
await accounts.registerRingVrfKey(0, { chainId: '0x22', junctions: [] });

// v0.11: rejects with RegisterRingVrfKeyErr.Unknown, reason "Bytes(32): expected 32 bytes, got 1"
await accounts.registerRingVrfKey(0, { chainId: peopleChainGenesisHash, junctions: [] });
```

Test fixtures are the usual casualty. Anything spelled `'0x00'` or `new Uint8Array(16)` for a 32-byte field has to
become the real length.

## Subscription interrupts

Three long-standing gaps in the product-side transport are closed. None changes the wire; all change what a product
observes from `Subscription.onInterrupt`.

### Every subscriber on a shared subscription is interrupted

Two `subscribe` calls with the same method and start payload share one host subscription. Only the first subscriber's
`onInterrupt` used to fire. Now every subscriber's does, with the same payload.

### A listener attached after the interrupt still sees it

An in-process host, and the container's default handler for an unimplemented subscription, can interrupt while the
`start` frame is still being delivered — before `subscribe()` has returned and before `onInterrupt` could possibly be
attached. That interrupt used to be lost, and the subscription sat silent forever. The transport now keeps the payload
and calls a late `onInterrupt` listener immediately, so the ordinary pattern is safe against a synchronous host:

```ts
const sub = payments.subscribeTopUpStatus(id, onStatus);
sub.onInterrupt(err => {
  // fires even if the host interrupted before subscribeTopUpStatus returned
});
```

The `VoidFunction` returned by `onInterrupt` in that case is a no-op.

### Re-subscribing after an interrupt starts over

An interrupted subscription is removed from the multiplexing table as part of its teardown, so a later `subscribe` with
the same parameters — including one made from inside the `onInterrupt` callback — sends a fresh `start` to the host
instead of silently joining a subscription the host no longer knows. `unsubscribe()` on an interrupted subscription is a
no-op; no `stop` is sent.

### Hosts: cleanup runs on a late interrupt

On the host side, a handler that calls `interrupt` after it has already returned now has its returned cleanup function
invoked, exactly as it is on `stop`. Previously the transport forgot the subscription but left the handler's own
listeners running, still calling `send` for a request the product had dropped. A handler that tidied up itself before
interrupting should make that cleanup idempotent, since it will now run twice.

The container's default handler for a subscription with no registered implementation interrupts synchronously; the
`queueMicrotask` it used to hide behind existed only to dodge the lost-interrupt bug above.
